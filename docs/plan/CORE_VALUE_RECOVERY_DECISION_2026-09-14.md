# 核心价值恢复裁决（2026-09-14）

## 结论先行

当前交付不能称为产品交付。更准确的状态是：

> **核心执行链路已经能跑通，但产品价值、结果可读性和决策可靠性尚未通过。**

用户打开现有手册后的合理反应会是“我到底应该看什么、系统到底判断了什么、凭什么相信它”。这不是用户不会使用，而是首屏没有把行动结论、证据边界和分析过程组织成一个可判断的结果。

当前不应继续扩展外围功能，也不应立即把全部代码丢弃。先进行一次有明确退出条件的核心价值抢救；抢救失败就停止自研产品，转用现成研究工具，保留需要时可复用的账本和证据接口。

## 关于“单轮就停止”

单轮本身不一定错误。对于一个明确的当前快照，如果一次取证已经覆盖任务合同、独立复核通过、没有待尝试的合法路径，继续调用模型只会增加成本和噪声，应该有界停止。

但当前系统把“hard requirement 已覆盖”当成了用户可以放心接受结论的主要信号，而本次运行仍有 stale/semantic gap，三个周期也没有校准结果。Review 发生在 synthesis 之后，只有 reviewer 明确要求补证才进入下一轮；当 reviewer 接受时，页面没有告诉用户“为什么不需要第二轮”。所以当前的 `1 round · 7/9 tools` 只能说明一轮取证结束，不能说明结论可靠。

可靠性必须拆成两层：

1. **执行可靠性**：调用是否真实发生、Evidence 是否有来源和时间、错误是否 fail-closed、Run 是否能恢复。当前这层已有相当多实证。
2. **决策可靠性**：关键数据是否齐全、结论是否被独立挑战、概率是否校准、是否减少人工返工。当前这层没有通过 G1。

后续界面必须明确显示：本轮做了什么、覆盖了什么、还缺什么、是否触发 challenge/replan、为什么停止，以及这个结果的使用边界。

## 根因裁决

### 1. 目标发生了漂移

原方案要求 M01 先交付“真实问题 → 真实取证 → 判断/限制 → 可读结果 → 可见过程”，并要求 M01/M02/M03 随真实案例推进。实际工作逐渐把完成测试、契约、恢复、观测和启动器当成了主要进度，用户最关心的“首屏能否读懂并采取下一步”被放在后面。这是执行取舍错误，不是用户要求不清楚。

### 2. 数据上限没有被当成产品决策

模型更换不能补齐跨交易所、OI 时序、实时 rates/USD 和事件分钟数据。当前数据只能支持保守的快照研究。若产品仍以“方向性交易判断”为主叙事，结果必然长期 neutral/no_trade，用户会觉得系统只是在解释自己为什么不能回答。

### 3. UI 把调试投影当成了产品流程

DSH 把原始对话和工具调用放在显眼位置，Desk 把 Evidence、Causal case、Review、Trace 纵向堆叠。信息确实存在，但用户需要自己从几十个事件中拼出结论。旧导航、无响应按钮和旧 Operations 状态还曾把基础设施状态冒充产品状态，进一步破坏信任。

### 4. 状态名称没有表达真实边界

`可发布`、`Evidence sufficient` 和 `completed` 描述的是账本或流程状态，不等于预测正确、可交易或数据充分。产品没有把这几个层次分开，导致“程序成功”被看成“研究成功”。

### 5. 缺少真正的停止规则

G1 已经是 `retain_baseline`，但工作仍然容易继续添加外围修复。没有一个“核心价值在几天内必须出现什么，否则停止”的硬规则，导致为了做而做。

## 唯一允许的恢复切片

时间盒：**3–5 个工作日，最多一个真实纵向切片**。切片只面向一个角色和一个任务：

> 手动提交当前 BTC/USDT 快照，输出“现在该做什么/不该做什么、依据是什么、什么条件会改变判断、下一次何时复查”。

允许修改的范围只有以下四项：

1. **先给行动结论**：报告首屏固定显示 `行动结论`、`使用边界`、`置信度上限`、`关键证据`、`未解决缺口` 和 `下一次复查`。在当前数据条件下，结论可以是“暂不交易/仅研究”，但必须让用户一眼看到，而不是藏在 horizon 或折叠区。
2. **显示可读的过程**：用一条短时间线表达 `输入 → 计划 → 取证（每步目的/结果）→ 充分度 → 独立挑战 → 是否补证 → 综合 → Gate`。原始 JSON、完整 prompt 和低层事件移到“展开详情”。
3. **把单轮停止说清楚**：若一轮结束，显示“停止原因”和“没有进入第二轮的理由”；若 reviewer 要求补证，显示第几轮、补什么、补证后结论是否改变。不能只显示 `Round 1/3`。
4. **清理运行状态**：Research 页面只保留当前真实可用的研究任务和结果；Operations 只显示 Hub、Research Worker、DSH Host/MCP 的当前 readiness 和最近失败。旧 observation、evolution、PPT、调度和无实现按钮从用户入口隐藏，原始排障仍可通过开发者详情取得。

数据不足时的硬规则：没有第二独立 venue 或 OI 变化序列时，不得在行动卡中给出方向性交易许可；只能输出研究性判断并明确缺口。不能为了让卡片更“像结论”而编造概率。

## 抢救验收清单

同一个真实问题连续运行至少 3 次，验收必须满足：

- 用户不展开任何调试详情，也能在首屏看到行动结论、适用边界和下一步。
- 用户能在同一页面回答：系统查了什么、哪些证据被采用、哪些过期/被拒、为什么停止、什么条件会推翻结论。
- 每个结论都能点回 Evidence ID；accepted、stale、缺口数量分开显示。
- 一轮停止时有明确 no-replan 原因；需要补证时能看到第二轮真实发生，而不是角色扮演或静态文字。
- 失败按“可重试 / 不可重试 / 仅诊断”分组；无关历史组件不出现在产品状态里。
- 三次运行的核心缺口、人工返工和结论变化都有记录；不能只以 hard coverage 100% 作为通过条件。
- 不宣称预测准确率、盈利能力或自动交易；若所有运行仍 neutral/no_trade，必须把它作为产品价值未成立的结果。

## 明确停止条件

满足任一条件，就停止继续扩展自研产品并执行现成工具方案评估：

- 3–5 天后首屏仍需要用户翻 Trace 才能找到结论或分析过程。
- 仍只有单一 venue、点状 OI、滞后宏观，且没有合规可持续的数据获取路径；三次运行都因同一缺口只能 neutral/no_trade。
- 相比现成研究工具，用户没有少查资料、少改写问题或少做人工返工。
- 仍出现“流程 completed / 可发布”但用户无法判断是否可行动的状态误导。
- 核心链路再次被契约、观测、调度、PPT、Evolution 或通用评测工作打断。

停止后保留：Evidence/PIT/Gate/Artifact 的可审计数据和必要 API；冻结当前 UI 与代码，不再投入新的平台层。若用户当前首要目标是获得市场研究结论，直接采用已有研究工具并手动维护数据来源，交付速度和实际信息量会更高。只有在自研链路能证明“可审计、少返工、少遗漏”这项增量时，才值得继续保留它。

## 独立复盘补充

本次并行审计中有一份独立只读复盘成功返回，结论与上文一致：不值得继续全面扩展，但值得做一次有界抢救。它建议把抢救样本收缩为一个可达的“有引用事件简报”，先建立每项 hard requirement 的 endpoint、字段、频率、窗口、许可、成本和 fallback 表，再用 2–3 个未来事件做真实观察；若要声称相对基线有价值，应使用 5–10 个同材料、同预算的盲评任务，要求 owner 明确优于基线达到 70% 以上、人工核验时间至少下降 30%、引用支持率达到 95% 且严重错误为 0。

这组阈值是继续投入的门槛，不是用来美化当前结果的指标。当前记录中的 `quality_success=0/6`、`manual_rework=6/6`、`usefulness=unlabeled` 和关键数据缺口都说明尚未达到门槛。
