## 2. 项目背景：用户想建的不是聊天壳

### 2.1 原始业务目标

用户希望在一个决策中心里，手动提交宏观事件、新闻或市场问题，让系统取得并核验材料，结合市场数据和历史背景，判断应如何理解事件、是否存在值得关注的交易机会，以及什么条件会改变判断。

当前以加密市场、尤其 BTC 宏观／市场研究作为首条验证链，但长期设想是一个可复用底座：上面可以有交易员角色入口，未来可能增加研究汇报、PPT 等能力。**首期以 BTC 验证，不等于把 BTC、三个预测周期或金融字段永久写死在核心中。**[U][D1 §2]

用户看重的是研究与决策的实际价值，不是已经部署多少 Agent、写了几层架构、是否能生成一份长报告。本轮不包括自动下单；方向性研究质量与真实预测／收益优势必须分别验证。

### 2.2 核心使用体验要求

系统应当做到：

- 重要事实确实通过工具取得，而不是靠模型记忆补齐。
- 信息不足时可以继续发现来源、读取原文、查历史或补算数据。
- 需要独立研究或复核时，真正运行独立任务，而不是同一个上下文扮演多人。
- 长期项目能够积累和恢复状态，但不会因为对话越长而越来越不可靠。
- 用户能看见计划、实际执行、失败、证据和结论改变，而不是在多个后台拼日志。
- 每项结果有明确依据、反证、限制与复查条件，能减少二次搜索和人工重做。

### 2.3 不能误读的价值判断

用户曾用“网页版可能 80 分、自建希望 90 分、实际可能 55 分”表达落差。**这是体验比喻，不是测出来的性能或质量评分。**[U]

其含义是：自建必须比现成产品增加价值，不能让用户为了“自己的架构”接受更差结果；也不能拿自动化、可追溯或更多插件去掩盖内容质量下降。

### 2.4 当前与未来范围

| 现在明确要做 | 未来保留且有阶段安排 | 当前不做 |
|---|---|---|
| 单 owner 手动研究、真实取证、补查、独立复核、主判断、当前任务可视化 | 可视化任务模板、排期和定时触发；更多数据与品种；后续产物能力 | 多租户、公开插件市场、自动交易、全面微服务化、多套 Harness 并存 |
| 核心历史资料、原文回读、确定性计算 | 经 owner 批准的定期数据更新与定期研究，两类分别授权 | 为未来可能用到而先安装全部数据平台、向量库、知识图谱 |
| 当前链必需的权限、幂等、续租、取消和提交一致性 | 实际瓶颈出现后的容量优化与恢复完善 | Redis/Celery/Kafka 等新 broker 先行、完整资源调度平台先行 |

## 3. 三个项目的关系：为什么用户认为自己在重走老路

### 3.1 相关项目

| 项目 | 在讨论中的角色 | 主要经验与遗留问题 |
|---|---|---|
| `luguochang/crypto-macro-decision` | 给 Codex 等工具使用的宏观决策 Skill 与部分数据脚本 | 方法规则较丰富，但执行保障不足；允许内部多角色审查作为真实子 Agent 不可用时的退路 |
| `luguochang/crypto-manual-alert` | 用户较早自建的手动触发分析项目 | 已有采集、结构化研究和框架集成，但关键路径的研究权限与循环被限制 |
| `luguochang/decision-hub` | 当前拟长期发展的决策中心主工程 | 运行、证据与审计能力较多；数据、上下文、真实协作、产品边界和质量闭环仍待打通 |

前序审查所用旧项目基线分别为 `crypto-macro-decision@7dd8d78`、`crypto-manual-alert@9b370f4`；当前主工程审查基线为 `decision-hub@1f5a31d`。这些是审查快照，不代表当前远端或用户工作区状态。[D4][D2]

### 3.2 Skill＋Codex 已经试过，不能当作全新建议

用户明确反馈：上下文过长后表现退化，感觉没有真正检索足够数据；Skill 里要求多 Agent 判断时，经常看起来仍然是一个上下文扮演多个角色。[U]

前序源码检查记录了几个能解释“允许退化”的设计：

| 前序检查内容 | 能说明什么 | 不能说明什么 |
|---|---|---|
| Skill 允许在用户未明确要求或子 Agent 不可用时内部执行四角色审查 | 完成条件允许真实独立执行与角色模拟混在一起 | 不能追溯证明用户每次 Codex 运行的实际工具权限和调用情况 |
| `agents/openai.yaml` 主要是显示信息和默认提示 | 文件名里有 agents 不等于定义了真实团队调度 | 不能断言 Codex 平台本身不能运行独立任务 |
| OKX 快照脚本主要提供当前状态，部分变化指标依赖另行取得历史 | 方法要求可能超出已有工具的真实能力 | 不能把当前 OI 或搜索摘要当成历史事实 |

**交接要求：不能再用“补一个 Skill，再交给 Codex”作为未经验证的根本解法。**可以将现成模型产品作为基线或未来工具消费者，但必须正面解决上下文与执行真实性。

### 3.3 旧项目不是完全没有多 Agent，而是能力在集成时被收窄

前序对 `crypto-manual-alert` 的审查记录：[D4 的 R15、U]

- 市场分析 Agent 使用 `tools=[]`，主要分析前置采集给它的材料；前置采集不足时，分析阶段不能自行继续研究。
- 研究配置限制一次子任务委派和一次搜索，将多个研究角度集中交给同一个研究者。
- 资料账本首次取得结果后，在该实例中复用整批结果，后续新查询不一定再次检索。

因此不能简单概括为“从来没接多 Agent”。更准确的说法是：**框架和子任务能力已经接过，但实际暴露的行为更接近受限单批次研究。**稳定性约束累积后，核心探索空间被缩小了。

### 3.4 decision-hub 的进步与重复风险

当前工程已经有多轮证据研究、正式 Gateway、Evidence/Fact/Artifact、事件窗口、失败保全与轨迹等资产。不能把它描述成从零开始，也不能因为结果不理想就全部丢掉。[D3][D4]

但仍存在同一个循环风险：

```text
提出“更聪明、更独立、更有证据”的目标
    → 集成更多框架与规则
    → 为稳定性和验收逐步限制行为
    → 工程链路更完整，但研究任务没有变好
    → 再换底座或新增架构
```

当前方案要打断的是这个循环，而不只是换一个技术栈。

## 4. 讨论如何演变：保留纠偏原因，避免重新走错

| 讨论阶段 | 用户提出的核心问题 | 当时的考虑 | 现在如何理解 |
|---|---|---|---|
| 初始项目检查 | 分层做了、DSH 接了、轨迹也有，但证据不足、效果差 | 先判断是不是数据与事实通路断裂 | 仍成立；不能把问题全推给 Agent 规则 |
| 自建价值比较 | 为什么不直接用 ChatGPT Pro＋搜索＋Skill？ | 比较现成能力与专用数据、计算、资产、流程的增量 | 自建不是为了通用“智力更强”，而是要证明专业研究增量 |
| 历史补充 | Skill＋Codex 和旧多 Agent 工程都试过了 | 发现上下文退化和角色模拟是建设动机，不是遗漏 | 不能未经验证退回同一失败路线 |
| 数据与整链方案 | 每一层怎么改，如何引入三个月数据和实时补查？ | 数据、解析、事实、检索、上下文、执行、提交逐层设计 | 保留，但按真实任务分批闭合，不先搭大数据平台 |
| 双前端与底座疑虑 | DSH 与 Desk 割裂，JSON、英文内部字段多，插件无感 | 核对宿主方式、DOM 耦合、插件与业务差距 | 一份自有业务工作区，迁移后退役重复 UI |
| 可观测澄清 | DSH 能否接 LoongSuite／Langfuse，究竟要加什么？ | 自动采集与业务埋点、原生 Trace 与研究关系分开 | 不造技术观测平台，也不指望 Trace 自动解释争议 |
| 架构可靠性质疑 | 方案顺着用户说，缺并发、队列、事务、恢复与可维护性 | V3 增加执行契约、源码风险探针和代码参考 | 必要约束保留，但不是所有控制工程都应先串行完成 |

用户明确批评过：助手多次顺着用户新增问题调整方案，结论不够稳定，缺少主动发现与独立反驳；有些回复过于抽象，没有落到代码和实际运行。[U]

## 5. 背景疑问登记：我们到底讨论了哪些问题

| 编号 | 问题／疑问 | 已考虑的关键因素 | 当前收敛结论 | 仍待验证 |
|---|---|---|---|---|
| Q01 | 自建比 ChatGPT Pro、Codex 的增量是什么？ | 通用搜索和提示已是基线，控制权不等于质量 | 用数据、确定性计算、研究资产和可验证流程证明增量 | 与简单基线的真实结果与返工对比 |
| Q02 | 长上下文为什么退化？ | 历史事实污染、原文淹没、摘要损失、宿主额外注入 | 长期研究状态外置；任务上下文短生命周期、按需回读 | 实际模型输入是否符合选择清单 |
| Q03 | 多 Agent 为什么变成角色扮演？ | 提示词允许 fallback，执行器没有强制任务回执 | 必要任务由真实执行保证，不用内部角色替代 | DSH 固定版本的独立调用、继承和取消接口 |
| Q04 | Team 是不是应该替代 Harness？ | 团队分工和运行基础是不同维度 | 复用 Harness，按任务决定分工；不追求全员聊天 | 独立任务是否带来互补证据和错误减少 |
| Q05 | 为什么数据越来越多仍没用？ | 获取、解析、入账、检索、上下文、推理均可能丢信息 | 按关键事实覆盖评测整链，不按来源数量验收 | 每个数据集的覆盖、可达性与许可 |
| Q06 | 三个月历史能否帮助预判？ | 回溯不足、修订、预热窗口、小样本、未来泄漏 | 热加载资料和索引，不是 prompt；只作为有边界背景 | 数据真实可得范围及是否改善研究 |
| Q07 | 有本地历史后是否仍然会补查？ | 缓存过度、capability 粗粒度去重、无效循环 | 保留缺口驱动 ReAct，区分新 query/target/window | 新行动是否真正取得新证据 |
| Q08 | Gate 太多是否把研究卡死？ | 所有任务套同一事实包，研究与交易许可混用 | 按任务合同分级；数据准入、研究充分度、发布权限分开 | 政策范围是否合理，有效正向路径是否成立 |
| Q09 | 代码分包为什么仍耦合？ | 目录边界不能约束业务责任，金融常量泄漏 | 核心、领域行为、适配器各有归属，行为测试保护 | 非金融产物能否不改核心完成 |
| Q10 | 要不要每个能力拆微服务或插件？ | 网络故障、状态复制、部署和版本成本 | 模块化单体＋少量必要 worker；可复用不等于必须内置 | 实测资源与故障边界是否需要单独进程 |
| Q11 | DSH 是否鸡肋？ | 已复用能力与跨语言、预览版本、UI 适配成本 | 本轮保留，不再频繁换宿主；失败到具体 seam 再裁决 | 公开接口是否足够，不靠 DOM/private patch |
| Q12 | 插件生态为什么没体现？ | 安装、启用、授权、业务接入与价值是不同层级 | 只接能关闭真实缺口的插件；不按安装数证明价值 | 每项能力能否进入真实研究和产物 |
| Q13 | 双前端为什么割裂？ | 两套提交、状态和报告入口竞争 | 一份日常研究工作区，Desk 必要功能迁移后退役 | 迁移后的输入、查询、链接、镜像构建与权限 |

### 7.1 当前方案中的职责归属

### 7.2 关于“通用底座”的取舍

可复用，不代表必须进入必需核心。正文解析、行情获取、PPT 渲染可以是可选共享能力；任务、证据引用、产物版本等稳定机制才适合保持通用。

PPT 在“将研究制成汇报”这一场景首先是产物能力，应消费有版本的研究结果及引用，不要重新搜一遍、重新猜一遍，也不应被强制满足 BTC 分钟数据门槛。

先采用模块化单体与少量必要进程隔离，不为每个 Agent、函数或 Provider 建服务。共享能力以真实复用或稳定外部协议为依据，不以“以后可能有用”无限扩建。[D1][D2]

## 8. 数据、历史与 ReAct：相关考虑必须一并交接

### 8.1 先按任务明确需要什么，不盲目增加数据量

研究事件变化、当前市场状态、已发生事件反应和方向性候选，需要的资料不同。官方原文、基线、事前预期、价格反应、衍生品状态也不是可互相替代的证据。

十篇转述同一公告的文章不是十份独立证据；CCXT、原生接口、OpenBB 都从同一交易所取得的同一个值，也不是三份独立数据。

### 8.2 三个月数据热加载的真正含义

热加载的是可查询数据、文档和索引，不是将原始历史全部放入模型上下文。展示窗口、指标预热窗口与回测／校准样本窗口分别定义。

数据必须显示实际覆盖、最早可读日期、频率、单位、合约类型、更新时间和缺失状态。不同来源历史回溯限制不同，不能承诺开源组件能免费补齐所有 OI、盘口、期权或事前预期历史。

历史使用分三类：

| 模式 | 含义 | 约束 |
|---|---|---|
| 当前研究 | 今天取得历史资料，用于理解当前问题 | 保留实际取得时间 |
| 真实观测回放 | 使用当时实际收到并冻结的资料 | 不加入后修订值或后来才知道的信息 |
| 历史重建 | 今天从档案和 vintage 重建过去背景 | 标记重建依据与限制，不当成前瞻成功记录 |

`received_at` 不倒填。只有日期而没有准确时间的发布信息，不能作为当天任意分钟已可知的事实。

手动回填使用持久游标、不可变分区和原子 manifest；Run 固定使用版本。回填旧事件不能触发一批新的实时研究。新数据发布可以热更新默认版本，但不在活跃 Run 内热换代码或插件。[D1 §6][D2]

### 8.3 本地检索与实时补查要相互补充

优先使用已有合格资料，但对过期、缺失或新事件执行实时刷新。统一能力沿现有 Gateway 提供：

`knowledge.search`、`knowledge.read`、`market.query_series`、`analysis.compute_features`、`knowledge.coverage`。

这些名字是实施规格，不是当前仓库已验证可调用的 API。结果需要包含来源、版本、可回读引用、缺口和实际失败原因。

新的 query、目标、时间窗、字段或版本可以构成新的行动。不能因为同一 capability 已经调用过，就把必要补查都禁止；也不能无限换同义词重试无权限接口。

### 8.4 不让模型替代确定性计算

收益率、OI 变化、资金费、基差、宏观差分等保留计算公式、输入引用、单位和窗口。未收盘 K 线、缺值、预测 funding 与实际结算、币数量 OI 与美元名义 OI、日频美元代理与分钟指数，都不能混用。

actual-prior 不等于 actual-consensus；历史分位不是未来方向概率；同时变化不等于因果。三个月材料可以增强背景，但不能据此声称 90 分研究或收益优势。

## 9. 长上下文、真实多 Agent 与研究质量

### 9.1 长期研究状态不等于长期会话

长期持久的应该是目标、证据、主张、未解决问题、报告版本与后续反馈。模型会话只是完成某一段工作的执行环境，可以换新和重建。

ContextManifest 记录任务需要的材料和版本。关键原文必须可回读，不依赖层层摘要；新证据、必要基线和反证不能被机械数量截断排除。

特别区分：

- `selected_inputs`：应用层选择的输入。
- `effective_inputs_verified`：实际宿主运行期输入已经验证。

DSH 可能额外注入规则、历史或工具说明。没有运行证据，不把选择清单冒充完整实际上下文。[D1 §7][D2 §11]

### 9.2 真实协作如何定义

真实独立任务必须有实际执行身份、输入清单、工具记录、结果与失败状态。独立不必从第一天就并行；M01 先完成一项真实独立核验，M02 再增加两项独立取证并行。

典型分工是：原文／基线研究、市场／数据研究、独立复核，随后干净上下文综合。计划声明、实际任务、执行 attempt 和原生 session 分开记录。

独立调查先不灌统一结论；复核针对具体主张与引用。多个任务结果先各自持久化，再形成固定复核输入，不并发覆盖一个共享报告对象。

### 9.3 多 Agent 不应制造假信心

相同模型、相同来源、相同材料可能产生相关错误。评价的是新增事实、发现遗漏、纠正引用或时间问题的能力，不是有几个 Agent 同意。

辩论围绕真实分歧进行：主张、质疑、补查、回应、采用／不采用／未解决，以及对报告的影响。没有分歧就诚实显示无分歧；没有独立任务就不能显示“团队复核通过”。

### 9.4 规则与权限不能绑成一个万能 Gate

数据准入、研究充分度和方向／执行权限分别判断。schema 通过只能证明结构，不能证明推理正确。

证据不足时不强行给方向，但已完成的事实研究仍可交付。反过来，“没有胡说”和“诚实弃答”只是底线，不能替代正常案例的价值。要让用户少查、少漏、少重做。

## 10. 双前端、插件与黑盒的最终考虑

### 10.1 DSH 保留的理由和边界

本轮保留是因为已有宿主、工具、会话、搜索、压缩和插件资产，整体更换成本尚未被证明值得。不是认为 DSH 永远最优，也不是用户不能质疑它。

前序确认的启动方式是固定上游构建＋官方插件安装；关键业务交互却有 DOM 依赖。目标是在公开业务 slot 中使用自有输入和视图，停止读取上游输入框文本或拦截原生发送。

若公开执行／交互接口无法满足核心任务，应记录具体接口缺口并裁决对应适配边界，不继续堆私有补丁，也不因为看到另一个热门项目就整体迁移。

### 10.2 Decision Desk 的处理

需要迁移后退出的，是重复的独立产品壳，不是底层业务能力。

| 处理 | 内容 |
|---|---|
| 合并到主工作区 | 研究输入、任务列表、报告、证据、取消、重试、反馈与必要数据健康 |
| 删除重复／无效入口 | 分散重复导航、多个名称同一抽屉、未接动作的装饰按钮 |
| 本轮退出默认产品 | Evolution／Promotion 主面板、自主演化 worker |
| 继续保留 | Evidence、Fact、Artifact、Outcome、Evaluation、必要权限和审计历史 |
| 迁移时同步修改 | 镜像构建、静态路由、workspace、链接字段、测试与部署入口 |

M01 复用已有能显示结果的能力，只修改首条链必需界面；M03 再完成必要迁移与重复 Desk 退役。不能先删可用于验收的页面，再陷入重写整个前端。

### 10.3 黑盒分为业务与技术两个问题

Hub 中保存并展示：

```text
Run → 计划任务 → 实际 Task/Attempt → 工具与资料
    → 主张 → 质疑／复核 → 补查／回应 → 报告修订
```

LoongSuite／Langfuse 展示模型调用、工具、时长、失败、用量与技术关系。任务树由真实业务回执生成，不是从 Trace 时间先后猜测；争议图也不能由固定角色名字自动拼出。

DSH 原生生命周期由插件采集，Hub 自有业务边界补少量 span；同一模型调用不能被重复采集和重复计费。

### 10.4 LoongSuite 与 Langfuse 的重要限定

前序发现已存在 OBS-01 的隔离接入和锁包记录，但默认需要显式启用，正文采集关闭，业务 Trace 链接未完整贯通。上游源码解释与锁定 npm 包行为要分别验证，不能混为一谈。[D3 §12]

原生子会话可能各自形成 Trace。接受多 Trace，通过真实 Run／Task／Session／Turn 与实际 Trace ID 关联，不为一张“超级图”伪造父子关系。Python 加一个装饰器或传一个 header，不保证接管插件私有采集器的上下文。

默认不采全部正文；调试开启需要权限、脱敏、留存和资源评估。仅有采集结构不能宣称可见完整输入，更不能承诺重建模型全部内部思考。

同一 DSH 内有多个子 Agent，不代表需要再启用 Pilot；不重复采集同一批工作。Langfuse 离线不影响正式研究提交；当前任务可见性不依赖它部署成功。

**当前任务可视化 M01 同期交付，完整选定诊断路线 M03 贯通。**这是最新优先级，覆盖旧版“观测平台先全部完成”的倾向。[D1 §5]

## 11. 可靠性、性能与维护：哪些必须现在修，哪些不能扩成外围工程

### 11.1 当前链的必要保护

固定 owner 认证、任务幂等、一个活跃主研究、既有租约续期与执行代次、原子结果提交、取消边界、真实事件记录、数据时间真实性、有界消耗，属于 G0——允许受控试跑的基础。

这些保护要和首个真实问题一起落地，不是另一项长期平台工程。未知远端状态可以先暂停并要求核对；不要求为了第一份报告先完成全量自动对账和自愈。

### 11.2 必须知道的执行语义

| 主题 | 应保留的考虑 |
|---|---|
| 幂等 | 同一稳定请求与同一幂等键返回原 Run；同键不同请求冲突；部署变化不偷偷切换原请求配置 |
| 租约与 epoch | 续租维持所有权；旧执行者即使恢复连接也无权覆盖新代次 |
| 提交 | Artifact、业务终态、完成事件、必要 Outbox 同事务；派生评价／观测失败不改终态 |
| 取消 | 数据库先撤销新执行权限；远端请求可能仍运行，不能虚构费用归零或已经停完 |
| 恢复 | checkpoint、Hub 和 DSH 不构成一个分布式事务；先对账，unknown 不等于未执行 |
| 外部唯一性 | 本地正式结果唯一可以保护；不轻易承诺跨供应商调用全局 exactly-once |
| 预算 | 未确认计费不直接退预留；为最终综合和必要复核留额度；未知不计 0 |
| 数据库 | 短事务、无网络等待、正确 Session 生命周期；SQLite 不立即换掉，但要尊重单机和写入边界 |
| 事件 | 数据库原子序号＋幂等事件；增量读取、断线重连和终态快照一致 |
| 升级 | 固定代码／合同／规则／模型／数据版本，未知兼容性不直接恢复旧 checkpoint |

### 11.3 并发与资源参数的地位

讨论中建议的试点初值包括 root=1、等待≤5、研究 leaf≤2、Gateway HTTP≤4、单 Provider≤2、重解析进程≤1。**它们是待测配置，不是已实现能力或不可调整的产品常量。**

网络等待用异步；同步数据库按短事务与受控线程边界处理；CPU／不可控重解析用隔离进程。取消 await 不等于停止运行线程。父协调等待时不占子任务需要的唯一执行许可。

Python Semaphore 只管它能控制的调用，不能宣称自动限制 DSH 内部模型和原生搜索。需要明确每条调用的上限与责任，但不为此先造全平台资源服务。

### 11.4 本阶段不做的“完善”

不引入新的分布式 broker、不全面迁移数据库、不追求高 QPS、不做多机弹性、不造通用账户系统、完整计费产品、可视化流程编辑器或多后端观测平台。必须先用实际报告和运行记录指出具体瓶颈。

不因“代码分了包仍耦合”就直接微服务化。服务、插件、模块、进程和 Agent 是不同维度；用真实责任和资源隔离需要决定边界。

备份、版本和恢复仍需在适用阶段落实，包括数据库、checkpoint、DSH 持久状态与被引用资料，不能只备份一份报告文本。

## 12. 调度的澄清：后续必须成为可视化产品，不是临时关闭

### 12.1 用户最新明确要求

未来要有任务面板，能看到任务模板、触发规则、未来排期、实际触发、执行状态、跳过原因和结果关联。现在优先保障核心有效，之后再正式建设和启用。[U][D1 §3、9]

### 12.2 三个不能混淆的层次

| 层次 | 表示什么 |
|---|---|
| 排期预览 | 按规则计算的预计触发时间，未执行、无研究副作用 |
| TriggerFire | 实际到期／尝试准入／跳过或阻断的记录 |
| Run／DataJob | 被正式接受的工作，进入已有执行与结果流程 |

预计触发不等于已入队；已入队不等于开始；触发成功不等于研究成功。暂停规则只停止后续新触发，是否取消现有 Run 走单独命令。

### 12.3 当前阶段的正确隔离方式

当前只允许 owner 显式研究；已接受任务内部补查、恢复和必要后处理不算新的用户触发。`next_review_at` 只是建议，不直接生成自动 Run。

但手动模式是集中 TriggerPolicy，不在各层永久硬编码。未来调度以 owner 批准的服务身份接同一个 Admission，而不是 body 自报 `scheduler` 就有权限。

定期数据更新与定期研究是不同授权。手动历史作业可先运行，不等于批准自动研究或把历史导入当新事件。

### 12.4 开源组件与后续落地范围

当前方案选择 APScheduler 的时间触发／计算能力、FullCalendar Standard 的 React 日历展示；Prefect／Kestra 仅参考产品交互。具体版本、标准版与高级功能许可范围在接入时重新确认。

M04 才新增完整 Schedule／Fire 数据与 UI，后端负责同一套预览和真实触发时间语义。不要在每个 API 实例开一个独立 scheduler，也不在调度回调里等待整段模型研究。

后续必须明确：时区、规则版本、漏跑合并、有效期、重叠、队列满、预算耗尽、撤销授权和幂等。已经发生的历史不能被改规则重写，配置升级不能暗中重派同一逻辑触发。

### 12.5 不返工的边界

现在保存 task kind、来源、parent/root、attempt、状态、输入／结果引用；后续将 schedule/fire 关联进来。当前与定时执行复用同一研究核心，不建设第二套定时 Agent 或另一个任务后台。

**调度只能放大已有能力。主研究未通过价值验证，不进入自动触发阶段。**

### M01 的三个切片

**M01-A：最小受控入口。**固定 owner、当前触发策略、续租／epoch、提交一致性、事件和有界权限，仅修首条链必需范围。

**M01-B：首个真实研究。**保存旧基线；按问题选择合同；真实原文／基线与已有行情；修相关片段和新目标补查；运行一项实际独立核验；干净综合。

**M01-C：同期可视化。**自有研究输入、计划与实际状态、关键证据、结果和失败／取消；不先重写整个前端。

### 两个阶段门

**G0：允许受控试跑。**保护当前执行与事实正确性，不要求先造完整平台。

**G1：值得自动化。**代表案例和独立留出案例达到冻结的研究、时间、引用与可使用性要求，用户确认可用于日常研究，才进入排期与自动执行。

### 16.1 第一次开工顺序

5. 交付真实报告／任务回执／引用及差异；无法运行时交付明确失败证据，不以 mock 成功替代。

不默认从重新画架构、安装全部 Provider、接齐整个 Langfuse 部署或制作排期日历开始。

### 16.2 开发协作与上下文规则

| 规则 | 目的 |
|---|---|
| 一个有效规格、一张当前任务卡 | 避免多版最终方案互相冲突 |
| Core 写路径／schema 一次一个负责人 | 避免并行修改状态与数据所有权 |
| UI／parser 可在冻结 DTO 后独立并行 | 保留开发效率，不让“防耦合”变成全部串行 |
| 新依赖必须说明收益、运行负担和不引入时的替代验证 | 防止为了复用反而嵌套多个平台 |
| 真实结果与故障样本随 PR 交付 | 避免只验收容易验证的工程结构 |
| 决策写 `DECISIONS.md`，状态更新在当前卡 | 不再新增另一份并列“最终最终方案” |
| 旧文档只按需要回读 | 不重现开发上下文退化 |

每次完成／中断交接固定包含：真实改变、精确 diff、实际执行的测试与输出、真实报告／回执或失败证据、未验证项与下一步。

### 16.3 什么时候应该停下来而不是继续扩张

连续提交只有类、schema、配置或图，没有推进当前真实问题时，停止外围扩张，回到案例。

研究质量无改善时，不进入调度；真实独立核验未完成时，不增加更多角色；数据确实不可得时，不反复加强提示词；宿主公开接口缺失时，不无限补 private hack。

停止扩张不等于认定项目没有价值。需要保留已证明有用的数据、工具和研究资产，并用证据裁决后续投入。
