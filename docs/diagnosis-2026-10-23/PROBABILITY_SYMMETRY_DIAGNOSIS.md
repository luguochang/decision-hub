# 事前方向概率"多空对称"问题排查记录

状态：只完成排查，代码还没改。修复方案需要确认后再执行。

## 1. 现象

用户反馈：事前概率里看多和看空的概率一样，"不动"那一项看起来没有提供信息，这样的概率和没给差不多。

结论：在这一份已保存的 ETH 4h 报告里，横盘是 20%，不是 0。如果其他页面显示横盘为 0，需要提供截图或 run id 再查。可能的来源是"未来 24 小时逆向波动风险记录"（`HistoryForecastRecord.tsx`），那张卡只有做多和做空的逆向风险，本来就没有横盘这一项，容易被看成"不动 = 0"。

## 3. 原因（按影响大小排序）

1. **设计问题（主因）：概率由 LLM 直接写出，没有量化的基准率。**
   `packages/runtime_adapters/dsh_runtime/perpetual_profile.py:225-265` 要求模型自己写情景权重和幅度，同时加了大量"不得编造"的约束。输入包里没有历史 4h 收益的分布、和 ±0.30% 阈值对应的历史频率，也没有趋势、波动率这类条件化信号。模型手上没有锚点，最稳妥的写法就是左右对称的无信息先验。
2. **路径分布太粗。** 三个点情景、±1% 对称幅度，算出来的期望收益正好是 0。所以开多和开空在扣成本后都不可能占优，结论只能是"维持空仓"。概率形状本身就锁死了这个结论。
3. **当期信息确实不足。** 事件 p/q 未知，快照超过 600 秒不满足确认门槛，资金费、订单簿、期权 IV 这些输入在这一轮都没进来（见 INCREMENTAL_DELIVERY_COVERAGE T-405/T-406）。
4. **提示词的约束偏向保守（次要）。** `perpetual_profile.py` 里反复要求"不得编造概率/幅度/校准"，但没有任何条款鼓励在有证据时偏离对称。`DECISION_HUB_PRODUCT_ARCHITECTURE_V1.md:534` 的 0.55 上限只适用于"单一搜索摘要/未确认消息"，不是全局上限；代码里是否执行了这条还没有核对。本次 40/40 远低于 0.55，所以这条不是本次对称的原因。

总结：信息不足是触发条件，主要问题在设计。系统没有一个"基准率 + 条件调整"的量化层，把这件事交给 LLM 在强约束下凭主观判断，结果就退化成对称先验。

## 4. 修复方向（待确认）

1. 研究输入里加确定性的基准率：用 OKX 永续 1 分钟原件统计近 N 天 4h 收益落在 >+θ、[-θ,θ]、<-θ 三个区间的频率，θ 用目标阈值；统计结果作为冻结原件随研究一起提交。
2. 模型只负责在基准率上做有证据支撑的调整，并逐条写出调整理由；没有证据就保留基准率，不再默认用对称值。
3. path_distribution 改成按历史分位数生成幅度，不再固定写 ±1%，这样期望收益才有可能偏离 0。
4. 审核项增加一条：方向概率和基准率相同、又没有写出理由时，必须标注"无条件信息"，界面显示为"仅基准率"，避免让人误以为这是研究判断。
5. 现有结果按 Brier 和 log loss 持续记分，并与"纯基准率"对照。只有跑赢基准率，才说明研究调整有价值。
