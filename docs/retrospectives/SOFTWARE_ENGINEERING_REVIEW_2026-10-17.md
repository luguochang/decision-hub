## 3. 为什么反复修改仍不能交付

### 3.1 总控文件已存在，但没有形成一致、可执行的交付控制

仓库已有产品总计划、完整PRD、33项需求核对、W0–W9、M1–M5和每个release计划。缺口是这些视图没有稳定表达同一个“现在”：tasks.json多个running任务停留在不同旧发布；current-core-execution.json仍嵌有大段历史。10月11日审计已经指出机器合同和清单状态漂移，后来仍出现相同管理问题。[历史明确发现](../design/market-risk-v1/CURRENT_REQUIREMENTS_AUDIT_2026-10-11.md:141)、[任务表](../design/market-risk-v1/executable-product-v1/tasks.json)。

推断：继续只增加“最新方案”，会增加下一次接续时的解释负担。总控需要收敛已有权威关系和完成证据，而不仅增加文字。项目早期“报告研究工作台”与后来的“事前行动、监控、学习”目标也需要明确版本边界，避免历史完成状态覆盖新要求。

需要区分：旧产品总计划已明确标记为历史参考，并非所有文档都在争夺当前入口。具体问题是当前入口内部也有过期状态：本轮暂停前，CURRENT_FOCUS下方仍称release33代码未开始，release33/STATUS和机器状态却已记候选修复及定向验证。暂停说明已放到当前入口顶部；历史文字保留供核对。[旧总计划的定位](../product/PRODUCT_EXECUTION_MASTER_PLAN.md:18)

### 3.2 跨层生命周期与时间预算靠连续补丁收敛，设计没有先贯通

真实失败先后发生在HTTP受理、原生Session、accepted后的proof、model binding、catalog、Provider input、终态结果读取。它们属于同一条执行链的不同接缝，不是同一个错误毫无变化地重复，也不是每次都能归因外部模型或Docker。

| 发布 | 保存的首要失败/现象 | 说明的问题 |
|---|---|---|
| normal26 | 多轮模型完成，技能loaded后仍list，领域节点未执行，Task总期限耗尽 | 模型活动不等于产品任务推进 |
| normal27 | Host已accepted，HTTP响应超时；父失败后子工具仍完成 | 受理、执行、取消和物理结束的边界 |
| release28 | 原生Session不存在，报告/行动为0 | 原生身份与恢复合同 |
| release29 | 35秒submit signal进入accepted后的proof | HTTP等待预算与后台研究预算混用 |
| release30 | model binding重复扫描大量源码/原件 | 认证成本进入主链且缺少统一性能边界 |
| release31 | 模型开始前catalog请求30秒失败，公开终态延迟 | 前置查询成本与失败传播 |
| release32 | 真实Provider前消耗约428.6秒；原始失败被结果读取错误覆盖 | 模型计时起点与终态首因权威 |

依据：[OP181–OP193](../design/market-risk-v1/executable-product-v1/EXECUTION_LOG.md:1796)、[release32根因](../../artifacts/decision-product-v1/core-main-flow-20261015/release32/BTC_FAILURE_ROOT_CAUSE.md)、[release33准备阶段计时证据](../../artifacts/decision-product-v1/core-main-flow-20261015/release33/PLAN.md:21)。历史根因中的“已证实”沿用具名原件审计，本轮未重放全部运行。

目标架构已经写了DSH负责模型/工具/技能、Graph负责研究生命周期、Hub负责事实/行动/结算。现有证据支持优先修订这些边界的执行合同；尚不足以断言DSH和LangGraph天然冲突或必须更换框架。[架构边界](../design/market-risk-v1/executable-product-v1/ARCHITECTURE.md:32)

### 3.3 认证与历史追溯的执行成本侵入研究热路径

release30实际model binding重复扫描约57,111文件；release31的catalog路径后经减少重复深认证降到冷读约1.64秒；release32的Provider input回调又主要耗在source capture、original auth和writer lifetime。[OP185/188](../design/market-risk-v1/executable-product-v1/EXECUTION_LOG.md:1843)、[release33事实](../../artifacts/decision-product-v1/core-main-flow-20261015/release33/PLAN.md:22)

推断：仅移动watchdog或逐入口加快查询，不足以证明整个链条成本已经受控。需要先决定哪些证据在生成/发布时完整认证、哪些不变证据可以按版本复用、每个执行边界必须实时复核哪些权限/取消/新鲜度。保存原件、禁止未来信息、身份隔离和幂等仍必要；“每个读取入口都重复遍历完整历史”则必须有明确必要性与成本依据。不能把性能、数据完整性和领域分析混在一个大函数里靠例外分支维持。

### 3.4 测试做了很多，但中间层没有提供足够的发布信心

不能说没有集成测试：已经有契约、数据库、跨层失败投影和局部PC集成。具体缺口是替身的行为与实际跨进程组合不一致。例如release32的终态测试经过Runtime/Worker/API，但Host替身直接返回unavailable，未覆盖真实Host把失败双空结果误判为binding mismatch的组合。[OP188](../design/market-risk-v1/executable-product-v1/EXECUTION_LOG.md:1873)、[测试替身](../../tests/research/test_terminal_error_provenance32.py:236)、[真实失败](../../artifacts/decision-product-v1/core-main-flow-20261015/release32/BTC_FAILURE_ROOT_CAUSE.md:46)

结果是：很便宜的局部门能证明局部规则；很贵的正式构建、启动、真实研究负责发现下一层基本接线错误。需要补足可重复的真实本地组件集成链，替身只放在明确的外部依赖边界，并用真实回执校验替身契约；再用有限真实Provider流程验证外部依赖。它既不能作为金融效果证明，也不能跳过真实Host/持久化/发布代码。

### 3.5 局部“只运行一次”没有限制整体返工循环

每个release的一次构建、一次提交可以避免重复提交和破坏现场，但release29→30→31→32仍在连续执行“窄修复→窄测试→全构建→启动→新真实研究→下一首败”。没有看到一个有效阻止同类跨层失败继续滚动发布的总层停止条件。[OP184–191](../design/market-risk-v1/executable-product-v1/EXECUTION_LOG.md:1828)

量化样本：release30/31/32正式构建分别用时16分49.141秒、16分42.839秒、20分39.928秒，合计**54分11.908秒**，三个版本均未交付完整BTC报告/独审/行动。release31/32的observer分别运行2140.906秒、2918.203秒；这些观察窗口可能与其他阶段重叠，不能相加当作总投入。统计支持“反馈昂贵且业务产出仍未完成”，不支持估算全会话费用或说所有时间均无效。[构建原件](../../artifacts/decision-product-v1/core-main-flow-20261015/release30/build-start.json)、[release31](../../artifacts/decision-product-v1/core-main-flow-20261015/release31/STATUS.md)、[release32](../../artifacts/decision-product-v1/core-main-flow-20261015/release32/STATUS.md)

需要限制的是工程反馈循环：一次变更究竟减少了哪个用户阻断，剩余全链风险是否已在便宜的集成环境验证。研究任务本身有真实进展时超过60秒是正常的，不能把开发止损规则变成研究硬超时。[用户原要求及计划约束](../design/market-risk-v1/executable-product-v1/CORE_MAIN_FLOW_EXECUTION_PLAN_2026-10-15.md:61)

### 3.6 我的执行和沟通也有直接责任

- 我把注意力不断收缩到最新错误，局部修复结束后继续下一轮，没有及时把同一故障族提升为架构与集成合同问题。
- 更新里大量强调测试数量、哈希、版本和一次性约束，而没有稳定回答“用户今天多完成了哪一步、还差哪一步、为什么这次能结束”。
- 多agent能复核给定补丁，若所有人只检查同一个局部假设，仍无法替代产品完整性检查和整链验收。
- 历史状态、当前任务和短接续文件持续膨胀且漂移，使接续更容易盯住局部。长度本身不能证明模型遗忘，但现有管理方式确实增加了错读风险。

这些是基于上述执行与状态证据的工程管理判断，不是把问题归责于用户反复强调要求，也不是对Superpowers插件缺陷的判断。

## 5. 总控计划应该怎样补：提案，尚未批准执行

建议整合已有总控，不再让一份新文档与旧计划并列成为另一个权威。保留历史原件；当前状态只保留一个简短入口。讨论确认后再把旧计划中的有效需求逐项映射进该入口。

总控最少应含以下内容：

1. **交付合同**：本版用户路径、界面应展示的真实内容、必须成功的业务动作，以及下版范围。BTC/ETH、核心事件、行动、持续跟踪、经验闭环与多资产不能悄悄移出需求；分期必须明确说明。
2. **当前能力矩阵**：每项仅标“设计/已实现/局部已验证/正式整链已验证/持续运行已验证”，分别列出预测效果状态；每项附最新版本、证据和阻断，历史信息放索引。
3. **架构合同**：状态所有者矩阵、跨进程接口、HTTP/准备/模型/任务期限的区别、取消/恢复语义、证据认证边界、查询读模型、事务边界。
4. **关键路径和在制限制**：一个正在交付的纵向切片；并行工作只能解决该切片的独立阻断。Kronos与跨资产候选不与主链同步改造。
5. **分层测试清单**：最小正向全链、直接影响金钱/身份/时间/重复动作的必要负例、真实外部依赖验证和PC验收；每一层写明替身边界及不能证明的内容。
6. **变更与结束规则**：每次修复标明被证伪的假设和用户结果变化；同类边界连续失败时先评审合同，暂停新增发布。不能以换release编号代替整体止损，也不能以存在未成熟长期样本阻止可用工程切片交付。
7. **操作与恢复手册**：一个可复用开发/测试环境入口、一个发布入口；失败原因直接关联阶段和责任组件。每次记录结论和证据链接，不复制整段历史。

这里的限制针对开发工作管理，并非降低研究上下文、模型能力或人为把后台研究截成60秒。

|---|---|---|
| ① 产品交付边界 | 用户从事件/资产到行动、提醒、结果/经验的完整使用故事；首版范围与后续范围 | 用户确认具体可见结果；不再只说“核心功能完成” |
| ② 现状与需求映射 | 已有/待接线/有缺陷/未实现，逐项有证据 | 不靠重新读全部台账判断当前情况 |
| ③ 架构与可行性 | 一个请求时序图、状态/预算/认证职责表、最难接缝的验证办法 | 对真实Host/持久化/Provider接入方式没有核心未决假设 |
| ④ 验收与发布 | 集成→真实外部→PC→恢复的分层验证和结束规则 | 关键失败能在适当层被发现；完整验收不承担所有调试 |
| ⑤ 开发计划 | 有依赖和用户交付物的任务，每项记录操作/结果/阻断 | 在前四项确认后才恢复实施，使用一个总控和一个当前目标 |

随后建议先恢复一个真实研究到行动的可重复纵向链，再把事件监控与提醒、结果/经验消费接通；BTC验证通道后复用到ETH。黄金、纳指、恒科通过资产适配接相同流程，各自验证数据/时区/机制/策略参数。Kronos继续作为独立模型候选，而不是完整决策系统的替代品。上述为待讨论安排，不是对原需求的删减。

## 7. 结论边界与需进一步核实项

- 本轮没有证明全部历史修改无价值；已有真实基础能力和局部成功必须保留复用。
- 本轮没有证明更换框架、增加模型、扩大token或简单去掉校验就能解决问题。
- 真实金融效果与工程可用性必须分别评价。用户需要有依据的具体方案；不应以“不能承诺胜率”为由拒绝交付操作条件，也不能将模型主观概率冒充经验胜率。
- 实际运行指标、测试替身真实性和跨层成本仍需在后续批准的技术评审中验证。本轮不重新运行，以免再次进入修复循环。
- 需要确认的第一件事：首个交付版本是否必须完整覆盖“事前情景/概率和行动→变化提醒→结果回看→可复用经验”，以及其中哪一环允许分期；已有授权不自动视为对本讨论稿的批准。
