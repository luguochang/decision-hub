# 发布原件保全的容量整改

状态：已确认容量缺陷，结构性整改待实施；不代替真实研究报告验收。

## 实际问题与当前修复

正式20发布清单为2,015,306字节；候选21在编译前的已知最小清单为2,132,452字节，超过既有2,097,152字节上限。此次UI、Host均未编译。失败原件见 `artifacts/mr-release-b2b4-21/build-execution.json`。

当前格式把各历史研究版本的每个资源路径、哈希重复展开到新发布清单。一次实际V3保全就增加254个资源引用，约61,726字节。因此只消除这一次未使用的V2胶囊，仍不能解决长期升级的容量增长。

候选21b只在真实选择记录、原发布和已捕获V3均通过认证时，省去新生成但未被任何落库Run选用的V2胶囊。原有30份归档、实际20的V3闭包和固定字节上限保持。该修复用于先恢复核心研究流程，完整标准发布与真实报告结果另行验收。

## 下一批的具体设计

1. 新增有版本的发布合同：当前生产源和当前构建产物仍逐项绑定；历史资源通过独立、不可变的归档索引引用绑定。索引包含路径、内容哈希、长度、原发布身份、研究依赖哈希和全部资源引用。
2. 索引以规范JSON内容寻址保存。发布清单必须验证索引本身、每个历史release索引和全部叶子原件；仅有文件名、缓存命中或注册记录不能授予有效身份。
3. 旧格式读取器继续可验证旧Run。新格式显式选择新验证器，禁止把旧receipt就地修改成新格式。旧Run仍绑定其实际安装receipt、原选择与原始会话。
4. 标准构建在同一停止/原件捕获/当前源封存流程中生成新索引，再验证并发布。标准启动只接受验证通过的格式。失败保留原件，并恢复上一正式版本。
5. API/报告的历史来源查询按原Run身份解析索引；真实用量、复核、permit和事务校验继续使用原数据，发布索引不替代这些证据。

## 验收与失败处理

- 使用真实20和真实历史选择的只读快照验证全部原资源哈希。迁移前后解析得到的资源集合和哈希必须完全一致。
- 对索引、叶子、原receipt、路径范围、循环引用分别做必要篡改控制；任何异常均拒绝发布。
- 对同一真实保全集合验证清单大小、解析时间和峰值内存；重复历史引用不得继续线性扩大主receipt。新版本不得靠提高字节上限通过。
- 一次标准发布后验收旧Run读取、新研究生成、完整报告和附件。只读校验不能代替真实用户流程。
- 若迁移验证失败，保留失败与新索引；旧发布和旧数据保持可用，修复具名缺陷后才重试。

此项属于MR02/MR28的可维护性整改，不增加预测效果资格，也不修改旧28日试验、旧fit或未来cutoff规则。
